# Slimming GLiNER multi PII v1: can it fit in 1.5 GB?

2026-11-22. Local only; synthetic cases only; 2 CPU threads; each model ran alone in a fresh process at below-normal priority.

## Decision rule (set before the numbers)

A challenger replaces the baseline only if it:

1. catches **at least 77.5%** of names
2. catches **at least 95%** of Malay, Chinese and Indian names
3. wrongly hides **at most 2.5%** of facts
4. uses **at most 1500 MB** of memory at peak (fresh process)
5. takes **at most 300 ms** per message at p95

Licence never blocks an owner's own use. It only decides whether a model can be bundled in a public library or must be an optional download.

## Recommendation

**Adopt GLiNER multi PII v1 (ONNX, embedding table int8 (maths fp32)).** It passes every rule: 80.9% of names caught, 100.0% of Asian names, 1.8% of facts wrongly hidden, 1314 MB at peak, p95 75 ms. Licence: OK for personal and company use; can be bundled.

**In plain words.** Yes: GLiNER multi PII v1 fits in 1.5 GB once its ONNX export has the embedding table (the 250,000-word vocabulary, about 70% of the file) stored as int8 and everything else left at full precision. Names caught are unchanged (80.9% against 80.5% for full size, same within noise), Asian names are 100%, wrongly hidden facts are 1.8% (the same), and peak memory in a fresh process falls from **3.1 GB to 1.3 GB**, with the slowest 5% of messages at 75 ms instead of 244 ms. It is the only slim form that passes the rule, and it fits the 1.5 GB limit.

**A correction to the first report.** It said full-size GLiNER needs 2.0 GB. That was memory *after loading*; the real peak, measured in a fresh process here, is **3.1 GB** (fp32 torch) or 2.4 GB (fp32 ONNX). The case for slimming is stronger than the first report said.

**What each slimming attempt did**

| Attempt | Result |
|---|---|
| Embedding table to int8, maths in fp32 (`onnx_emb8`) | **Passes.** 554 MB file, 1.3 GB peak, spans identical to fp32 on the smoke sample. |
| gliner's own whole-model int8 export (`onnx_int8`) | Quality destroyed: 14.4% of names, 21.5% of Asian names. Do not use. It is small and fast, and wrong. |
| fp16 (gliner's export, then converted) | Not usable. The converter's default and no-shape-check settings produced files onnxruntime refuses to load (type mismatch on Cast nodes); a third setting (keep Cast nodes in fp32) had not finished after about 50 minutes of CPU and was stopped. Not measured. |
| 8-bit MatMul weights on top of emb8 (`onnx_emb8_mm8`) | Same quality (80.6% of names, 100% Asian, 1.8% wrongly hidden) and 1.1 GB peak, but 444 ms median and 551 ms p95 per message: fails the 300 ms limit. 8x slower than emb8 for 0.2 GB less memory. |
| Plain fp32 ONNX (`onnx_fp32`) | Same quality as torch, 3.5x faster (55 ms vs 193 ms median), but 2.4 GB peak: fails the memory limit. |

**What this measurement includes.** Peak memory is for a process that loads `gliner` (and so torch) to run the ONNX file. A leaner runtime that does gliner's small amount of text pre- and post-processing itself and loads only onnxruntime would use less than 1.3 GB, but that is **not measured here**.

**Cost to switch.**
- **Disk:** the model file is 554 MB (today's model: 106 MB; full-size fp32: 1.1 GB), plus about 20 MB of tokenizer files.
- **Memory:** 1.3 GB peak and about 1.1 GB once loaded, against about 0.23 GB for today's model. If that is still too much to hold all day, the detector can be loaded only when a send needs it and released after a few idle minutes; that is a code choice and is not tested here.
- **Code:** `ops/local/pii_model.Detector` keeps its interface. Two ways in: use the `gliner` package (quick, pulls in torch: about 1.2 GB more to install), or write the small decoder directly on onnxruntime and tokenizers (about 150 lines, no new dependency kind, more work and its own tests). Either way the file hashes are pinned like today's model.
- **Risk:** all numbers are on synthetic cases; a model change in a redaction path needs a mutation run and a check on more statement layouts before it ships ON. It would ship OFF by default.
- **What we'd lose:** about 40 ms per message (17 ms today against 55 ms median) and about 1 GB of memory, in exchange for names caught going from 45% to 81% (Asian names 78% to 100%).
